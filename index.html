Experiment harness

corpos-lab

Controlled behavioral experiments on local language models.

Language models fail in consistent places: decision points where the locally obvious move is the wrong one. This lab measures whether describing those points back to a model changes what it does, and whether the description format does the work or just the information it carries. It runs studies against local models with llama.cpp, scores each run against a declared rubric, and records what actually executed — the model the server reports, its build, the sampler, the processor, and the repo commit. Each assay runs in a single-use container pinned by image digest, and a hard gate holds the code to a 95% coverage floor. The instrument is Go; the findings are eight preprints on Zenodo. An earlier version ran on a strict pre-registration charter that turned improving the method into a kind of failure; I retired it, documented why, and rebuilt the lab around recording what each run actually did.

Eight preprints on Zenodo, and the finding from each
  • Phenomenological descriptions induce analysis-mode behavior ↗ Describe a decision to a small model instead of telling it what to do, and it analyzes the description rather than acting; a concrete action spec brings the action back.
  • Content over format, and how grounding recovers execution ↗ What suppresses action is the information, not the descriptive format; a plain rule carrying the same content suppresses it just as much, and grounding the guidance in the concrete domain is what restores execution, across four models.
  • Comprehension as compliance ↗ The synthesis of the program: grounded content, not wording, moves a small model to act, and giving it a tool loop recovers many decisions it had only described, though some gaps survive.
  • Canon suppression in corpus-loaded assessment ↗ An evaluator loaded with a project's own framework missed real findings that a fresh observer caught, a caution for anyone who scores agent output with a model that already knows the system.
  • Duty or corpus: guidance form is model-dependent ↗ Whether the form of an instruction changes behavior depends on the model: a prescriptive duty beat an equivalent descriptive version on one model, tied on another, and helped on neither for a third.
  • Derived or observed: a first-principles duty's coverage ↗ A procedure written from first principles reads as self-contained but prevents no more failures than no method at all, and a hazard the task cannot reveal gets covered only once you name its category.
  • Correct verdicts, wrong field: attribution vs capability ↗ A model can give the right answer while misreporting what drove it, so verdict accuracy and the model's own account of its reasoning are both unsafe as proof that the field you intended did the work.
  • Thinking-trace analysis ↗ A method for mining an agent's planning text to find recurring failure points, and to tell whether the overhead is the system's fault or the agent's, which decides how you fix it.

model-router

Start cheap, escalate on evidence, cap the frontier.

Running every step of an agent on a frontier model is simple and expensive. This library starts each turn on the cheapest model that might do the job and climbs to a stronger one only when the turn gives it a concrete reason — a repeated tool error, a parse failure, a mid-turn fault — then walks back down when the trouble passes. A frontier budget caps how often any turn can reach the top tier. It is pure Go with no dependencies, and every model call sits behind one small interface, so the whole routing engine is tested with no model and no network. A runnable demo prints the tier decisions on a fake ladder.

MCP server

library-mcp

A Model Context Protocol server for a classified reference library.

A small server that gives an AI agent a reference library it can read and write. Each entry is a source filed under a Dewey number, with three short notes: what it establishes, what question it answers, and when to reach for it. Those notes let the agent judge whether a source is worth opening before it spends context reading it. It speaks the Model Context Protocol over stdio and keeps everything in one SQLite file, so it runs with nothing else attached. Pure Go, no C toolchain.

CLI tool

corpos-gate

A stack-agnostic gate a repo declares as data and runs across languages.

Every repo grows a bespoke pre-commit script that drifts from the next one's. This tool is the one orchestrator behind them. A repo lists the checks it wants in a gate.yml (format, lint, build, tests, a coverage floor, a vulnerability scan) at one of three nested stages, and corpos-gate runs the plan. It drives each language's own tools, so the gate matches how the project is already built. It covers Go, TypeScript, and Python today, and can extend to any language. Point it at an existing app and init detects the stack and seeds the coverage floor from the app's own config. One built-in check refuses any commit that weakens the gate. The core is sans-IO, and the repo gates itself with its own binary in CI, at 97.6% coverage today against its own 95% floor. corpos-lab runs on a gate.yml of its own, so the two tools gate each other.
